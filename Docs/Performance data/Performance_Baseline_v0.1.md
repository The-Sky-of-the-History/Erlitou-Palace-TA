# 性能基准测试报告 (Performance Baseline) | 夏朝白盒+初级材质场景 v0.1

时间：2026.11.10  
项目：UE 5.8 二里头「夏朝」场景（宫城区 + 5 号四排府库 + 3 号地宫）｜考古导向环境美术复原  
版本：白盒基线 v0.1（2299 个 StaticMeshActor 复用 60 个网格、17 樘 BP\_Door、3 块 Landscape，未做合并与 LOD）  
方向：国风大世界 ｜ 场景编辑 / 场景制作

## 一、为什么先测，不先优化

这个阶段把宫城、5 号四排府库、3 号地宫全塞进同一张地图，一共 2324 个 Actor、2334 个静态网格组件，全部由 Shape\_Cube / Shape\_Cylinder 拼出来，没有 LOD、没有合并、没有流关卡。此时谈优化没有意义——没有基线，改完之后"感觉快了"是不算数的。

所以先做一件事：固定三个典型视角，用同一套口径各采一组数，把"现在到底卡在哪"钉死。三处视角的选择标准不是好看，而是覆盖三种负载类型：

· **宫城区俯瞰**：整个场景入镜，测的是"总量"；
· **3 号地宫巷道**：室内近景，窄墙互相遮挡，测的是"遮挡剔除到底有没有生效"；
· **5 号 D01 门前**：交互距离内，测的是"玩家真正站的地方"。

## 二、测试口径

机器：Intel Core i9-14900HX（24 核 32 线程）／NVIDIA GeForce RTX 5060 Laptop（驱动 32.0.15.9611）／16 GB 内存。

命令与设置：`stat unit` + `stat fps`；`t.MaxFPS 144`；`r.VSync 0`；编辑器视口屏幕百分比 67.6%（渲染分辨率 1374×860，输出 2032×1260）。渲染设置保持项目默认，未改渲染管线。

采样方法：每个机位连续截 3 帧，取中位值，不取最好也不取最差。`stat unit` 一次同时输出 Frame / Game / Draw / RHIT / GPU，比单看 FPS 更有用——FPS 只是 Frame 的倒数，看不出是 CPU 还是 GPU 在拖。

必须写明的一点：**这是编辑器视口的数据，不是打包版。** 编辑器会 tick 全部 2324 个 Actor、还会跑编辑器自己的 Slate 与选中高亮，所以 Game Thread 这一列偏大且几乎与视角无关（下面读表会看到）。要拿运行时数据，必须打包成 Shipping 再测一次，这一条列在待办里。

## 四、读表：四个反直觉的数字

**一、面数最高的视角，帧率反而最高。** C 的 136 万面是 A 的 2.4 倍，FPS 却是 88.6 对 69.2。原因不是 GPU 有魔法，而是 C 的可见批次只有 770，比 A 少 260 个——镜头怼在门框上，背后大半个场景被遮挡剔除掉了。**决定帧率的不是场景里有多少面，而是这一帧真正提交了多少批。**

**二、Game Thread 与视角几乎无关。** A 14.28、B 12.68、C 11.31，跨度为 3 ms，而三个视角的可见面数相差 2.4 倍。这说明编辑器视口下 Game Thread 的开销主体是"tick 这 2324 个 Actor"，跟镜头看哪儿关系不大。**这一列现在不能用来判断场景本身的重不重，只能用来判断 Actor 数量级。**

**三、Draw 与 GPU 都在 8 ms 上下，且始终低于 Game。** 三个视角 Draw 7.67–8.13、GPU 7.60–8.01，全部卡在 8 ms 附近；而 Frame 已经到 12–14.8 ms。**这一版是 CPU 侧先到顶，GPU 还有富余。** 后续优化如果只盯着贴图与面数，收益会很小。

**四、B 视角的 976K 面不能按字面理解**（事后单独查过，见第八节）。全关卡静态网格三角面合计只有 406,340，地宫 M09 巷道 47 个墙体 Actor 全是 48 面的 Shape\_Cube、合计 2,256 面。`stat unit` 的 Prims 在同一机位、同一画面下能从 2.87 万跳到 111.8 万，把静态网格全部隐藏它反而涨到 111.8 万——这个数字混进了阴影 / 预通道 / Lumen / VSM 等非主视图工作。"每批 1.14K 面"是分母污染出来的假象，不能用来判断墙体轻重。

## 五、优化待办（按预期收益排序）

1. **合并静态墙段。** 现在 1501 个 Shape\_Cube 实例各自是一个 Actor，A 视角 1030 个批次里绝大部分是墙。把同一排的墙合并成 Merge Actor 或换成 HISM，目标是把宫城视角的 Draw Call 压到 300 以内。验证方法：同机位复测 A，看 Draw Call 与 Draw 线程时间是否同步下降。
2. **给远景做流关卡。** 2324 个 Actor 同时 tick 是 Game Thread 偏高的直接原因。按"宫城核心区 / 5 号四排 / 3 号地宫"拆三个子关卡，用 Level Streaming 距离加载，先把不看的那部分停 tick。验证方法：A 视角只加载宫城核心区，对比 Game Thread。
3. **地宫墙体这一条销案。** 实测 47 个墙体全是 Shape\_Cube、单件 48 面（第八节），不需要简化，也不需要换 Nanite。真正要追的是同一机位 Prims 在 2.87 万与 111.8 万之间跳变——那是统计口径与渲染器状态的问题，不是美术资产的问题。
4. **门蓝图去掉常驻轮询。** BP\_Door 现在是 Enhanced Input Action → Branch(CanInteract) → Branch(bIsOpen) → Timeline → 每帧两次 SetRelativeRotation，逻辑本身不重，但 17 樘门各挂一个 Tick 与一条 Timeline，叠加起来是可观的常驻开销。改成"进入交互范围才注册输入"，关门后卸载。
5. **测试口径固化。** 这次为了看真实上限把 `t.MaxFPS` 开到 144、VSync 关掉；但屏幕百分比是 67.6%，换机器就不可比。下一轮把屏幕百分比固定成 100%，并且必须补一次打包版（Shipping）数据。

## 六、没测到的，以及为什么

**交互瞬间的 Game Thread 峰值没取到。** 计划是在 PIE 里站到 D01 门前按 E，连按 10 次采峰值。实际执行时，合成按键进不了 PIE 视口——键被编辑器视口截获（按 W/E 直接切了视图模式），而 Python 侧也拿不到注入通道：`PlayerController` 的 `Player` 属性是 protected，读不出来；`PlayerController` 没有 `input_key`；只剩 `unreal.SubsystemBlueprintLibrary.get_local_player_subsystem()` 一条路，但它要 LocalPlayer 实例，拿不到。

所以 C 行只能给出"门前稳态"，开关门那一下的峰值要么人工按一次 E 采，要么等打包后用 `stat unit` 复测。**这一行先留空，不编数。**

不过这一轮顺带量到了一个更有用的东西：**噪声底**。同一机位连按 10 次 E（门未实际开合），Game 在 11.05–11.33 ms 之间抖，极差 0.28 ms。而 BP\_Door 开门时每帧只做两次 SetRelativeRotation（左右门各一次），按蓝图节点量级估算，增量在 0.1 ms 上下——**低于这个噪声，编辑器视口里本来就不可能分辨出来**。也就是说，"交互瞬间 Game Thread 跳 3 ms"这类说法，如果不在单帧 trace（Insights / `stat game` 逐帧）里看，多半是把抖动当成了峰值。这一项的结论要等到打包版用 Insights 抓单帧才成立。

**打包版数据没取。** 编辑器视口里，Game Thread 含着编辑器自身的 tick，绝对值不能直接当运行时帧预算引用；能用的只有"三个视角之间的相对关系"。

## 八、附录：地宫「97.6 万面」溯源实测

机位与第三节 B 组完全相同（X 34600 / Y 53360 / Z −1040，pitch 0°，yaw 0°），口径同第二节：编辑器视口 67.6%（1374×860），`stat unit` / `stat scenerendering`。

### 8.1 要查的问题

B 组读到的是 **855 个 Draw Call、976.0K 三角面**，平均每批 1,140 面；A 组是 1,030 批 / 562.3K，平均每批 546 面。同一套 Shape\_Cube 拉出来的墙，地宫看到的面数密度是宫城的两倍，与"白盒全部由 48 面的立方体拼成"这个前提不符。

当时的猜测是：某几段墙被拉得特别长，UV 与切线数据被撑大，或者碰撞体复杂度被算进了渲染面。这一节就是去核对这件事。

### 8.2 结论先行

1. **地宫墙体本身没有问题。** M09 巷道 47 个墙体 Actor 全部是 `Shape_Cube`，单件 48 面，合计 **2,256 面**——比宫城里一根圆柱（512 面）还少。
2. **全关卡静态网格一共 406,340 面**，全部实例、全部 LOD0 相加，也凑不出 976,000。
3. **`stat unit` 的 Prims 不是"这一帧画面里有多少三角面"。** 同一机位、同一画面，它读出过 28.7K，也读出过 1,118.0K；把静态网格全部隐藏，它反而从 973.6K 涨到 1,118.0K。所以 `976K ÷ 855 = 1,140 面/批` 是分母污染出来的伪指标，不能用来评价墙体轻重。
4. **真正可用的量是**：B 视角基础通道 **465 个 Mesh draw call**，Base pass **0.10 ms**，可见三角形在 **2–3 万** 量级（渲染器状态稳定后读数 479 批 / 28.7K）。

### 8.6 为什么这个数字会骗人

三条互相独立的证据：

1. **总量对不上。** 全关卡静态网格 406,340 面，M09 巷道 2,256 面。976K 不可能是"墙的面数"。
2. **隐藏反而变大。** 把所有静态网格隐藏（8.5 第 6 行），Prims 从 973.6K 涨到 1,118.0K。一个"画面三角面数"的指标不可能在画面变空之后变大。
3. **同一画面能差 40 倍。** 恢复后（第 7 行）是完全相同的画面，读数是 28.7K，正好和 465 个基础通道 draw call × 约 48 面/件相自洽。

所以 Prims 里混进去的是**主视图之外的工作**：阴影深度、深度预通道、Lumen 表面缓存、虚拟阴影贴图分页等。第 5 行的地形就是活证据——站在离地面 10 m 以下的地宫里，地形一个像素都看不见，它仍然贡献了 396 个批次和 32 万面，只可能来自这些非主视图通道。

还有一个旁证：这组操作前后，视口左上角"光照需要重建（2,476 未构建对象）"的提示消失了，说明渲染器状态在这期间发生了切换。973.6K → 28.7K 的跳变更可能是光照 / Lumen / VSM 重建与缓存造成的，而不是几何变了。这一条是推断，没有单独验证。

**当时的判断错在哪：** 拿一个混了所有通道的计数器当"可见面数"，再除以混了所有通道的批次数，得到的"每批面数"既不是墙的面数，也不是墙的批数。要判断资产轻重，只需要读网格自身：48 面、1 个材质分区。

### 8.7 以后该看哪个数


| 目的          | 用哪个                                                  | 不要用                     |
| ----------- | ---------------------------------------------------- | ----------------------- |
| 判断某个模型重不重   | 网格自身三角面数（`get_num_triangles`）、材质分区数                  | Prims ÷ Draws           |
| 判断这幅画面的提交量  | `stat scenerendering` → Mesh draw calls、Base pass 时间 | `stat unit` 的 Prims 绝对值 |
| 判断 GPU 是否吃满 | `stat unit` 的 GPU 列、`stat gpu` 分项                    | FPS 单值                  |
| 判断某一帧的峰值    | Insights 抓单帧 / `stat game` 逐帧                        | 连续截图取最大值                |


另外两个方法学坑，记下来省得下次再踩：

- `set_is_temporarily_hidden` 对 Landscape 无效，验证隐藏要用 `ShowFlag.Landscape 0`；
- `r.Shadow.Virtual.Enable 0` 在本项目里不生效（读数完全不变），不能用它做阴影差分。
